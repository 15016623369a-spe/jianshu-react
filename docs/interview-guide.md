# 面试表达指南：见数

## 一、60 秒版本

> 我做了一个垂直的 Evidence-gated Agentic RAG，叫见数。  
> 它解决的不是“把问题变成 SQL”，而是“数字按什么口径、依据哪份政策、如果证据不够要不要拒答”。  
> 用户问 2027 年 1 月净营收，系统会解析查询月和规则月，检索生效政策和公告，核对账本，执行只读 SQL，返回金额、文件行号、版本和绑定参数。  
> 我做了 150 题多域评测，模型兜底 150/150，错误出数 0，正常路径 P95 4.45 毫秒；工程上有 301 项测试、版本化文档、ACL、历史导出、结构化观测和 HTTPS 冒烟。  
> 它不是通用 Agent 平台，而是一个受控、可审计、能拒答的垂直 Agentic RAG。

## 二、三分钟结构

### 0:00 问题

普通 Text2SQL 能生成 SQL，但企业问题里数字往往和口径、版本、公告、账本绑在一起。

### 0:40 方案

```text
范围解析
→ 检索政策/公告/手册
→ 判断证据缺口
→ 补查 / 模型兜底 / 拒答
→ 只读 SQL
→ 金额与引用核验
```

强调：不是自由 ReAct，是受控状态机。

### 1:40 结果

```text
A1：211 / 220 / −9
双月方向：+46.40 / +40.80
4 个 buried-backlink 题需要模型补查
150/150，错误出数 0
```

### 2:20 工程

```text
301 tests
MD/HTML/PDF/DOCX
policy/manual/retail
历史 / 导出 / ACL
HTTPS 双账号冒烟
观测 / 备份 / 并发
```

### 2:50 边界

## 三、高频问题

### Q1：这和普通 RAG 有什么区别？

普通 RAG 是“检索文档 → 生成一段话”。  
见数是“检索证据 → 判断够不够 → 执行 SQL → 核验金额和引用 → 不够就拒答”。  
关键不是生成，而是证据门槛和可核验。

### Q2：这和 Text2SQL 有什么区别？

Text2SQL 关注 SQL 是否正确。  
见数还要回答：

```text
这个数字按什么政策？
政策哪个版本？
公告有没有缺失？
退款用哪个账本？
比较方向是谁减谁？
```

### Q3：为什么不用自由 ReAct / Multi-Agent？

因为这是金额和版本场景，错误代价高。  
我选择有界状态机、有限工具、有限重试、失败即停。  
Agentic 不等于自由循环；受控决策也可以叫 Agentic RAG。

### Q4：150 题怎么来的？是不是自测？

是内部多域评测，不宣称第三方独立评测。  
拆分是 policy 60、manual 45、retail 45；覆盖正常命中、缺信息、无覆盖、错版本、冲突、循环和方向反转。  
模型兜底 150/150，离线确定性 146/150，错误出数 0。

### Q5：怎么保证不出错数？

```text
先证据后 SQL
多段生效日期切分
账本和上限绑定
金额与引用逐项核验
冲突/循环/缺失停止
```

### Q6：为什么不做通用平台？

通用平台需要任意文档、任意数据库、任意 domain 和大量 connector。  
我选择垂直深度：政策、手册、零售三个 domain，把证据、版本、权限、评测做透。  
通用内核有，通用平台不做。

### Q7：最大的技术难点？

不是调用模型，是“证据不足时停”。  
例如公告缺失、政策冲突、引用循环、部分月份无覆盖，系统都不能返回半截金额。

### Q8：如果重做一次？

- 更早冻结评测集；
- 更早把 trace/指标做成产品能力；
- 不把 UI 实验入口带到主流程；
- 先做 2–3 个 domain 的深度，而不是追求格式数量。
